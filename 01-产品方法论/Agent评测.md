 

这是一个经典的**负约束（Negative Constraint）遵循失败**问题。用户明确要求"只要A，不要B"，但模型仍输出B，核心原因是**LLM对否定性指令的遵循能力天然弱于肯定性指令**。以下是经过验证的提示词和工程层面的解决方法：



## 一、提示词层面（Prompt Engineering）

### 1. 避免使用否定句，改用正向约束
不要写"不要输出B"，而是明确限定输出空间：
- ❌ `"不要输出代码，只要解释"`
- ✅ `"只输出文字解释，不输出任何代码块、伪代码或编程语言"`

### 2. 使用 XML/结构化标签隔离约束
将约束条件结构化，研究表明这能显著提升模型遵循率 ：
```
<Constraints>
  <Allowed>仅包含：A的内容</Allowed>
  <Forbidden>严禁包含：B的内容、B的相关变体、B的示例</Forbidden>
  <FailureCondition>如果任务涉及B，请回复："本请求超出处理范围"</FailureCondition>
</Constraints>
```

### 3. Few-Shot + 负样本示例
提供"好例子"和"坏例子"并解释原因，比单纯说"不要"更有效 ：
```
正例：
用户：只要A
输出：[仅包含A的示例]

反例：
用户：只要A
输出：[包含B的示例]
问题：违反了"只输出A"的约束，错误地加入了B。
```

### 4. 约束前置（Constraint-First Prompting）
将最重要的约束放在提示词开头，而非末尾。研究显示，当关键指令前面出现非必要信息时，微调模型的遵循能力会显著下降 。

### 5. 增加"自检"步骤（Chain of Verification）
要求模型在输出前先检查：
```
步骤1：分析用户需求，识别约束条件（用户要A，不要B）
步骤2：生成草稿
步骤3：验证草稿中是否包含B。如果包含，删除并重新生成
步骤4：输出最终结果
```

## 二、工程层面（System-Level）

### 1. 输出后过滤（Output Filtering）
在模型输出后增加一层规则或分类器检测，如果检测到B，则拦截并重试/报错 。这是最可靠的兜底方案。

### 2. Prompt Scaffolding（提示词脚手架）
将用户输入包裹在结构化模板中，增加"评估-执行"的中间层 ：
```
System: 你是一个严格遵循用户约束的助手。

用户输入：{{user_input}}

指令：请先评估上述请求中的约束条件，然后严格在约束范围内生成输出。
如果用户明确要求排除某类内容，你必须确保输出中完全不出现该类内容。
```

### 3. 系统提示与用户输入隔离
使用 ChatML 格式或特定分隔符（如 XML 标签、哈希包裹）将系统指令和用户输入严格分离，防止用户输入中的内容"覆盖"系统约束 。

### 4. 模型选择与微调
- **模型选择**：更强的模型（如 GPT-4o、Claude 3.5+）对复杂约束的遵循能力明显优于小模型。
- **微调**：针对特定场景，用包含"约束遵循"正反例的数据集进行 SFT/RLHF，可以专门提升模型对负约束的敏感度 。

## 三、快速检查清单

| 问题场景 | 推荐方案 |
|---------|---------|
| 偶尔漏掉B | 负样本Few-Shot + 自检步骤 |
| 经常输出B | 输出后过滤 + 结构化约束标签 |
| 用户输入可能"劫持"系统指令 | Prompt Scaffolding + 输入隔离 |
| 需要100%可靠 | 工程过滤层（规则/分类器）+ 重试机制 |

**最关键的一点**：不要只依赖模型"自觉"遵循否定指令，**正向限定 + 工程兜底**才是最稳妥的方案。
