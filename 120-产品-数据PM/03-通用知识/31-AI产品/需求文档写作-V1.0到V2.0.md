# 需求文档 V1.0 → V2.0：4大能力升级，合格文档造就靠谱人设

**视频来源**：秀明 · 需求文档完整指南 第四期（V1.0 → V2.0）
**发布日期**：2025-01-29
**延续案例**：手机号验证码注册

---

## 一、V2.0 的定位

- **定义**：合格版。大多数研发能接受，认为产品经理比较靠谱。
- **核心变化**：从"自己能看懂"升级到"别人愿意看、看得舒服、看完能干活"。

## 二、4 大能力升级总览

| # | 升级维度 | V1.0 状态 | V2.0 状态 |
|---|---------|----------|----------|
| 1 | **照顾阅读者** | 格式基本整洁，但缺乏标记体系 | 用符号标记按钮、条件、报错等，一目了然 |
| 2 | **逻辑深度** | 有流程图，自洽 | 增加**时序图**，表达跨系统/跨部门的接口与协作 |
| 3 | **交互细节** | 描述粗略 | 用结构化表格明确每个字段的必填、样式、校验规则 |
| 4 | **数据/字段认知** | 未涉及 | 引入 UID 等常用表字段，理解底层数据结构 |

## 三、升级 ①：照顾阅读者——格式标记体系

### 3.1 名词解释（新增章节）

**为什么需要**：
- 你是"上帝视角"的文档编写者，其他人都依赖你的文档
- 同一个术语在不同公司、不同组织、不同项目组含义可能不同
- 尤其是**新增一个完整项目或模块**时，必须让所有人从一开始就能对齐理解

**示例**：

| 术语 | 解释 |
|------|------|
| **UID** | 用户注册账号的唯一 ID，是用户表的索引 |
| **Toast** | 一种轻量级弹窗提示，显示几秒后自动消失（类似烤面包弹出的感觉） |

> "后面那句（索引）不懂可以不写，但前面的定义一定要写。"

### 3.2 符号标记系统

V2.0 在流程图的文字描述中，引入了一套**视觉标记**，让阅读者不用细读就能快速识别各元素类型：

| 符号 | 标记对象 | 示例 |
|------|---------|------|
| **【】** 双括号 | **按钮**（可点击元素） | 【注册新账号】【发送验证码】【注册】 |
| **+** 号 | **多个并列条件**（且的关系） | 手机号格式正确 **+** 手机号未注册过 |
| **斜体 + 横线** | **校验/报错文案** | *请填写正确的手机号* |

**效果对比**：
- V1.0：全部文字堆在一起，"我自己录的时候都不想读"
- V2.0：一眼能看出哪个是按钮、哪个是报错、哪些是复合条件

> **金句**："没有技巧，全是感情（用心）。你能以始为终地想把这个文档写好，这个心很重要。"

## 四、升级 ②：逻辑深度——时序图

### 4.1 为什么需要时序图

- V1.0 的流程图只讲**业务流程**（用户视角的动作序列）
- V2.0 需要表达**跨系统、跨部门的协作关系**——谁调用谁、接口是什么、数据怎么流转
- **B 端产品经理尤为重要**

### 4.2 时序图基本结构

```
用户（客户端）          账号中心（后端服务）          短信服务商
    |                        |                        |
    |----点击发送验证码------>|                        |
    |                        |                        |
    |                        |--校验手机号有效性------>|
    |                        |                        |
    |                        |--生成6位验证码--------->|
    |                        |  绑定手机号+验证码      |
    |                        |                        |
    |                        |--组装短信内容---------->|
    |                        |--调用短信服务接口------>|
    |                        |                        |
    |                        |<--返回发送结果---------|
    |<--反馈发送状态---------|                        |
    |                        |                        |
    |----填写验证码---------->|                        |
    |----提交注册----------->|                        |
    |                        |--验证手机号有效性       |
    |                        |--校验手机号+验证码关系   |
    |                        |--创建新账号（UID+手机号+默认密码）|
    |<--返回注册结果---------|                        |
```

### 4.3 时序图三个纵向主体（本案例）

| 主体 | 角色 | 职责 |
|------|------|------|
| **用户（客户端）** | 最前台 | 触发操作、展示结果 |
| **账号中心** | 中间服务层 | 生成验证码、绑定关系、校验、创建账号 |
| **短信服务商** | 外部服务 | 接收短信请求、返回发送结果 |

### 4.4 时序图关键知识点

**① 校验的"双重保险"**：
- **前台校验**（页面层面）：即时提示用户格式错误，给用户一个 Toast 或行内提示
- **后台校验**（接口层面）：当前台请求到达后端时，后端再次兜底校验手机号有效性
- 两处校验目的不同，**都要写清楚**

**② 验证码生成与绑定**：
- 验证码为 **6 位纯数字**
- 生成后与手机号**绑定**，关系保留 **10 分钟**，超过则删除
- 10 分钟内相同手机号重复发送 → **不产生新验证码**（关系不变）
- 这里就回答了 V0.1 时研发的疑问："连续发两个验证码，两个都能用吗？"

**③ 同步 vs 异步结果**：
- 调用短信服务商后，可能**实时返回**发送成功/失败
- 也可能只返回"接口调用成功"，**实际发送结果异步回调**
- 具体取决于与短信服务商的约定——产品经理需要了解这种可能性

**④ 接口描述（入参/出参）**：
- 入参（Input）：你给接口什么数据
- 出参（Output）：接口处理完返回什么数据
- 示例：调用短信服务接口 `sendSMS`，入参包含手机号、短信内容模板等

**⑤ 图文映射关系**：
- 时序图中的序号（1→9）与下方文字描述的序号**一一对应**
- 文字不是独立于图的，而是对图的详细注释
- "图让人快速看全貌，文字补细节"

## 五、升级 ③：交互细节——字段级结构化描述

### 5.1 交互表格（新增）

将页面上的每个输入元素用表格描述，确保**前端工程师一看就知道怎么做**：

**手机号字段**：

| 维度 | 内容 |
|------|------|
| **必填** | 是（必填性校验：未填时提示"请填写手机号"） |
| **样式** | 文本框（Text Input） |
| **Placeholder** | 请输入手机号 |
| **逻辑** | 默认无特殊逻辑 |
| **校验** | 中国手机号：11 位纯数字，首位为 1；校验不通过提示"请填写正确的手机号" |

**验证码字段**：

| 维度 | 内容 |
|------|------|
| **必填** | 是 |
| **样式** | 文本框 |
| **校验** | 不单独校验位数/纯数字，仅校验与系统发送的验证码**是否匹配**；不匹配提示"验证码错误" |

**区号下拉框（教学示例）**：

| 维度 | 内容 |
|------|------|
| **样式** | 下拉框（Dropdown） |
| **选项** | 枚举：中国大陆（+86）、其他地区… |
| **校验** | 无需校验（下拉选择，值已枚举） |

### 5.2 交互表格的价值

| 框架 | 作用 |
|------|------|
| **必填** | 强迫自己想到必填性校验，不会遗漏 |
| **样式** | 明确前端用什么组件（文本框/下拉框/单选等） |
| **Placeholder** | 前端直接可用，不用猜 |
| **逻辑** | 如有联动、默认值等特殊逻辑，在此说明 |
| **校验** | 每个字段的校验规则 + 对应报错文案 |
| **备注** | 补充信息，可选 |

> **金句**："这不是点状需求文档能给你的东西，这是一个好的结构**强行**给你带来的逻辑严谨性。"

## 六、升级 ④：数据/字段认知

### 6.1 为什么要懂数据表和字段

- 在写需求文档时，能合理引入字段名（如 UID），让研发知道你理解底层结构
- 创建新账号时，你需要明确写清楚要创建哪些字段：

| 字段 | 说明 |
|------|------|
| **UID** | 账号中心生成的唯一标识，可用随机算法（雪花算法/哈希等） |
| **手机号** | 用户提交的注册手机号 |
| **默认密码** | 可选——取决于产品设计 |

### 6.2 关于默认密码的两种产品方案

| 方案 | 说明 |
|------|------|
| **方案 A：无密码** | 基础服务不设密码，每次登录都用手机验证码 |
| **方案 B：注册时填写密码** | 在注册流程中增加"设置密码 + 确认密码"的交互步骤 |

> 具体选哪种由产品经理根据产品定位决定。如果使用默认密码，建议用**随机算法**而非"123456"之类的弱密码。

| 维度 | V1.0（入门） | V2.0（合格） |

## 九、贯穿全篇的核心理念

1. **文档不怕细，越细越好**——研发不会嫌你写得多，只会嫌你没写清楚
2. **以终为始**——写之前想清楚这份文档的读者是谁（研发、测试、设计），他们需要什么
3. **图文互补**——图给全貌，文字补细节，两者有映射关系，不是分离的
4. **引用关系 = 可维护性**——通用内容抽成独立用例，其他地方引用而非复制
5. **时序图在 B 端尤为重要**——不会画先学会看，理解系统间的调用链路
