## 两边怎么分工

| 内容 | 飞书多维表格 | 本地 Obsidian |
|---|---|---|
| 投递清单 | 作为结构化总表，按公司、状态、时间筛选和排序 | 保持同样的一行记录，便于在秋招知识库内查阅 |
| 岗位 JD | 上传 PDF 到“岗位JD”附件字段 | 保存 JD 原文件到 `10-原始材料/13-JD/`，在对应行写文件名或双链 |
| 投递项目 | 填写项目名称 | 使用 Obsidian 双链连接到项目介绍、复盘和面试材料 |
| 简历版本 | 上传本次投递使用的 PDF | 保存 PDF 到本地简历目录，并记录文件名或链接 |
| 投递状态 | 使用单选字段更新状态，便于筛选 | 使用相同文字同步更新表格中的状态 |
| 详细准备材料 | 只在备注中保留摘要或链接 | 放在秋招库对应的公司、岗位、项目和面试文件中 |

使用原则：飞书适合做“投递台账”和筛选统计；Obsidian 适合沉淀 JD 原文、项目材料、简历版本和面试复盘。两边的投递记录必须一一对应，详细内容不需要重复复制，只需通过文件名、双链或备注互相定位。

### 2. 飞书多维表格：`lark-base`

飞书操作统一使用 `lark-cli base +...`，不要使用旧版 `+table`、`+record` 聚合命令。当前固定参数：

```bash
BASE_TOKEN='NTmXbqlLPaf9ZMsx0guccyXDnKe'
TABLE_ID='tbl7X23kjlyvU5WZ'
```

常用命令：

```bash
# 查看字段，确认真实字段名和类型
lark-cli base +field-list --as user \
  --base-token "$BASE_TOKEN" \
  --table-id "$TABLE_ID" --format json

# 新增一条投递记录；fields 与 rows 的顺序必须完全一致
lark-cli base +record-batch-create --as user \
  --base-token "$BASE_TOKEN" \
  --table-id "$TABLE_ID" \
  --json '{"fields":["岗位名称","公司","录入时间","投递时间","投递项目","投递状态","备注"],"rows":[["AI产品经理","字节跳动","2026-07-25 10:00:00","2026-07-25 10:30:00","剪映音色克隆项目","已投递","官网投递"]]}'

# 查询投递记录
lark-cli base +record-list --as user \
  --base-token "$BASE_TOKEN" \
  --table-id "$TABLE_ID" --limit 200 --format json
```

### 3. JD 与简历 PDF：`record-upload-attachment`

附件不能作为普通文本写入，必须先创建记录，再使用附件命令上传 PDF：

```bash
# 先从新增记录结果中取得 record_id，再上传 JD PDF
lark-cli base +record-upload-attachment --as user \
  --base-token "$BASE_TOKEN" \
  --table-id "$TABLE_ID" \
  --record-id 'rec_xxx' \
  --field-id '岗位JD' \
  --file './JD-字节-AI产品经理.pdf'

# 上传本次使用的简历 PDF
lark-cli base +record-upload-attachment --as user \
  --base-token "$BASE_TOKEN" \
  --table-id "$TABLE_ID" \
  --record-id 'rec_xxx' \
  --field-id '简历版本' \
  --file './简历-林承列-AI产品经理版.pdf'
```

注意：`--file` 只接受当前命令工作目录下的相对路径。若 PDF 在 Obsidian 仓库中，先将文件复制到当前工作目录，或在该目录下执行命令；不要直接把绝对路径传给 CLI。

## 当前是否有专用同步脚本

目前没有单独的自动同步脚本；同步由 `work-secretary` 维护本地 Markdown，由 `lark-base` 调用 `lark-cli` 维护飞书表格。这样可以避免自动脚本误改 JD、项目和简历文件。若后续记录量变大，再单独创建同步脚本，并先用 `--dry-run` 检查变更。
