

# 百度秒哒 · 项目介绍稿（产品经理视角）

---

## ① 我的背景

我在百度负责「秒哒」这款 AI 原生无代码应用开发平台的核心链路产品设计，覆盖从需求分析、MVP 设计与验证、内测数据回收、问题定位迭代，到试点推广的完整产品生命周期。

---

## ② 当前目标 / 卡点

**业务目标：** 让中小企业非技术员工和个人创作者，能通过自然语言把创意快速落地为可商用的应用，解决"有想法但不会写代码"的核心痛点。

**核心卡点有两层：**
- **用户侧：** 非技术用户连 PRD 都写不了，遑论开发，传统低代码门槛依然过高；
- **产品侧：** AI 生成的应用质量不稳定、复杂需求识别不准、token 消耗高——三者叠加导致"可用性差"，用户留不住。

---

## ③ 目标拆解 → 业务数据锚点

为了让目标可衡量，我将"让用户真正用起来"拆解为三个维度的量化指标：

| 维度 | 核心指标 | 目标值 |
|---|---|---|
| 应用质量 | UI + 功能综合评分 | ≥ 80 分 |
| 搭建效率 | 平均创建时长 | ≤ 10 分钟 |
| 用户留存 | 7 日留存率 | ≥ 25% |

这三个指标并非拍脑袋，而是通过竞品对标和用户调研倒推出来的合理基线——下一步展开。

---

## ④ 业务数据拆解 → 我的思考链路

**竞品分析给我三个关键判断：**

- Bolt / Lovable 代码生成能力强，但完全面向开发者，对非技术用户不友好；
- 阿里秒悟与生态打通，但操作流程复杂，目标用户重叠度低；
- 市面上没有一款产品同时做到：**极简输入 + 办公场景专项优化 + 企业级可用性**。

这个缺口就是秒哒的差异化空间。

**用户调研给我三层需求结构：**

```
基础需求：自然语言创建应用，降低编程门槛
    ↓
期望需求：生成结果可用、可迭代、可复用
    ↓
潜在需求：高质量模板 + 微调即用，进一步降低创建成本
```

这个三层结构直接决定了 MVP 的功能优先级划分（P0 / P1 / 后续迭代）——不是"想到什么做什么"，而是需求分层驱动功能排序。

---

## ⑤ 思考链路推导 → 预期收益

基于以上判断，我预期通过产品设计能拿到：

- **质量层面：** 应用质量评分从基线提升至 80 分以上；
- **效率层面：** 平均创建时长控制在 10 分钟以内，token 消耗相比初版降低 45%；
- **留存层面：** 7 日留存 ≥ 25%，验证产品对目标用户的持续价值。

## ⑦ 围绕产品指标 → 具体做了哪些动作

### 动作一：MVP 核心流程设计（指向：创建成功率 + 创建时长）

设计了完整的应用创建链路：

> 用户输入自然语言 → 意图识别与需求澄清 → 场景匹配 + 功能推荐 → AI 生成 PRD → 用户确认/修改 → 实时构建 → 可交互预览 → 迭代/发布

其中有两个关键设计决策：

- **需求澄清模块**：当 query 模糊时自动弹出 3-5 个针对性问题，避免"理解偏差→重做"的恶性循环，直接提升一次创建成功率；
- **场景匹配 + 功能推荐**：将用户需求归类至"数据收集 / 业务管理 / 展示汇报"等核心场景，自动推荐该场景下的必备功能（如数据收集场景推荐"导出 Excel""数据筛选"），解决"用户不知道自己需要什么"的潜在需求问题。

同步交付配套功能——时光机版本管理（回退风险降低）、应用广场发布（复用率目标），形成完整产品闭环。

---

### 动作二：建立评估体系，驱动应用质量提升（指向：质量评分 62 → 82）

内测完成后，质量评分初版仅为 **62 分**，问题不是"好不好"的感受，而是"哪里不好"说不清楚。

我独立设计了 **UI + 功能双维度、三分七档评估体系**，配套核心场景评测集，建立闭环优化机制：

```
评估打分 → 归因分析（是 Prompt 问题 / 上下文问题 / 模型能力问题）
    ↓
调优策略（Prompt 优化 / 场景专项训练 / 组件库统一）
    ↓
复评验证 → 进入下一轮
```

通过这个机制，核心场景评分从 **62 分提升至 78 分（内测阶段）**，试点后进一步达到 **82 分**，累计提升 32%。

---

### 动作三：上下文工程优化，解决复杂应用生成的效率与成本问题（指向：tokens -45% + 功能完整性 ≥ 90%）

内测中发现两个深层问题：
- 复杂应用生成耗时长，且随对话轮次增加出现"注意力衰减"——功能遗漏率上升；
- 每次修改都要重新读全量代码，token 消耗居高不下。

针对这两个问题，我做了两个产品 + 工程联合设计：

**① Todo List 任务拆解机制**
强制将复杂任务拆解为多步骤节点，实时更新完成状态，有效对抗注意力衰减，功能完整性从内测阶段提升至 **90%**。

**② 索引机制（上下文工程）**
Agent 在首次创建应用后，自动生成"功能模块 ↔ 代码位置"的结构化描述文档；后续迭代时，基于索引文档快速定位目标代码块，无需重读全量上下文。结果：**tokens 消耗降低 45%**，复杂应用生成时长也显著缩短。

---

## ⑧ 各动作分别提升了哪些指标

| 动作 | 核心提升指标 | 结果数据 |
|---|---|---|
| MVP 核心流程设计（需求澄清 + 场景推荐） | 创建成功率、创建时长、人均创建数 | 创建成功率 75%，平均创建时长 8 分钟，人均创建 2.3 个 |
| 评估体系 + 闭环优化机制 | 应用质量评分 | 62 → 82（+32%），满意度 7.5 → 7.9 |

## 最终项目成果

- **全量上线**，试点效果通过评审；
- 应用质量评分累计提升 **32%**（62 → 82），tokens 消耗降低 **45%**；
- 已覆盖 **200+ 业务场景**，试点用户 200+，7 日留存 70%；
- 验证了"自然语言创建可用应用"产品路径的商业可行性。
