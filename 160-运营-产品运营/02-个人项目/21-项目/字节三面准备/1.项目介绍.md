
## 项目一：猎聘招聘 Agent

**这个项目是为了解决一个问题：HR 在猎聘主站搜人搜不准。**

我做了四步。

**第一步，需求洞察。** 我访谈了 30 家中小企业 HR，把搜不准拆成两类：第一类是平台接收到需求但处理不好，比如设了 25 到 30 岁，筛出来经常超龄；搜"数据分析"，候选人工作经历里明明写了相关内容，系统只匹配标题，搜不到。第二类是需求根本进不了系统，比如 HR 想要某类公司背景的候选人，不方便写进 JD，平台没有给这类隐性需求表达通道。

**第二步，策略决策。** 第一类可以在传统搜索上优化，但第二类靠打补丁解决不了。所以我们判断引入大模型 Agent，让 HR 通过对话说出真实意图，解决第二类；同时用 Agent 对搜索结果做二次语义筛选，优化第一类。

**第三步，MVP 落地。** 我和搭档基于 Hermes 框架魔改通用逻辑，替换成招聘场景逻辑，接入猎聘的搜索数据和推荐策略编排成 Skill，做多维交叉筛选加语义级岗位理解，替代原来纯关键词匹配。4 周交付 MVP，22 名真实 HR 试用，60 多条反馈驱动 4 轮迭代，推荐准确率从 60% 多提升到 85% 以上。

**第四步，工程化上线。** 确认可行后，沉淀决策文档移交给研发正式上线，后续持续迭代。

## 项目二：猎聘 MCP Server / CLI

**这个项目是为了解决一个问题：AI 人才在主流招聘平台上没有自动化的求职体验。**

我做了四步。

**第一步，需求洞察。** 我调研发现 AI Native 用户天然追求自动化求职，这批人在技术社区传播力很强，但没有任何招聘平台开放过 Agent 调用能力。谁先做，谁就能用极客体验撬动这批人自然裂变，同步扩大供给端提升 B 端价值。

**第二步，策略决策。** 我们把招聘流程拆成三组可被 Agent 调用的原子能力：查找职位、职位投递、简历完善。其中简历完善拆成 5 项子动作，设为投递前置条件，确保 Agent 投递前简历已经完整，避免无效投递冲击 HR 对简历质量的信任。

**第三步，MVP 落地。** 按 AI 团队、技术产品团队、外部用户三个圈层分层灰度，覆盖 50 到 60 人。定义硬性发布门槛：至少 30% 用户完成 1 次投递、至少 20 条有效反馈。

**第四步，验证闭环。** 实际 50% 用户完成投递，远高于主站投递率，200 多个 AI Native 人才新增注册加沉睡激活，MCP Server 正式上线。

## 项目三：美图海外 AI 证件照


**这个项目是为了解决一个问题：美图海外 APP 需要新增长点，而海外证件照市场存在明显的供给空白。**

我做了四步。

**第一步，需求洞察。** 我用「竞争密度 × 增长潜力」矩阵做市场扫描，发现国内同类工具 30 多款，头部占 70%，增长见顶。而海外每年 1.2 亿人办签证留学务工，线上工具不到 5 款，多数用户仍去线下照相馆，单次 20 到 50 美元。判断这是低竞争、高刚需市场，且美图的人像 AI 能力可以无缝迁移到证件照场景。

**第二步，策略决策。** 破局点定为 AI 全自动化替代线下。技术侧构建三个能力：100+ 国家尺寸精准裁剪、多肤色补光算法、动态合规库实时追踪各国政策变化，保障 100% 过审。商业侧双线推进：C 端免费生成转付费下载，依托美图海外 5 亿用户矩阵引流；B 端对接 snapfoto 和 7-11，打通线上生成到线下打印的闭环。

**第三步，MVP 落地与迭代。** 先自测模型能力基线确认链路跑通，再完成产品设计和交互方案。上线后独立跑通 A/B 实验，900 万样本两周分流。同时搭建全球政策爬虫系统，规格变动实时推飞书群，确保 24 小时内完成模型适配。

**第四步，验证闭环。** 上线首月获客 10 万以上，获客成本 2.3 美元，GMV 从单日 2000 增长到 2 万，10 倍突破，NPS 78 分远超竞品。

## 项目四：面宝（猎聘 Hackathon 一等奖）

**这个项目是为了解决一个问题：面试官在简历筛选、面试准备、评估打分全链路效率低下。**

我做了四步。

**第一步，需求洞察。** 梳理后发现面试官三个核心痛点：简历筛选低效、面试准备依赖经验、评估标准不统一。市面工具大多只做了简历解析，没有把面试前后完整链路串起来。

**第二步，策略决策。** 用 SDD 驱动，把面试官助手拆成面试前、面试中、面试后三个阶段的完整闭环。

**第三步，MVP 落地。** 基于 Claude Code 先写清产品设计文档，再生成前后端代码，0 到 1 交付可运行 Demo。覆盖简历解析、JD 匹配、AI 约面、面试题生成、实时记录与报告输出，题目支持按技能层、情景题、深挖题、项目经历分类，并能和简历内容联动定位。

**第四步，抽象沉淀。** 把人才 Mapping、定制化面试题、面试表现解析提炼为「岗位画像建模 → 问题智能生成 → 评估结构输出」的通用范式，复用到后续招聘垂直工具设计中。最终获 Hackathon 一等奖，项目正式内部上线。

# 评测
以下是面试中可以口述的版本，整体结构是：**评测分两大块 → 每块怎么设计 → 如何回应潜在质疑**。

---

## 猎聘 Agent 评测方案

**我们的评测分两大块：第一块测搜索结果的质量，第二块测 Agent 全链路的稳定性。**

---

### 第一块：搜索结果质量——Agent 搜出来的人，是否比主站更准

**具体做法是：** 我们选了 20 个真实在招的岗位，覆盖猎聘主站上搜索难度最高的中高端职位。针对每个岗位，找不同部门的用人方（就是实际负责面试这类岗位的人）来做离线评测。评测方式是盲测——每个岗位，我们分别用主站和 Agent 各召回 20 条候选人，打乱后交给用人方做匹配度评分，他们不知道哪批来自主站、哪批来自 Agent。

这样做的好处是：**用人方本身就是最知道"什么人合适"的人，他们的判断比任何算法指标都接近真实业务价值。** 而且盲测设计消除了主观偏差——评分只基于候选人与岗位的匹配度，不基于推荐来源。

**这里面试官可能会追问两个问题：**

**第一个，为什么用内部人测，会不会有偏差？**

这里的关键是：我们不是让内部人"主观评价 Agent 好不好"，而是让他们做**客观的匹配度排序**——这 40 个候选人里，谁最适合这个岗位。这是一个比较判断题，不是主观打分题。而且我们选的用人方是实际在招同类岗位的人，他们对"什么人合适"的判断标准和真实 HR 是一致的。后续上线后，我们还会用真实 HR 的搜索数据做持续验证，离线评测只是第一步的准入门槛。

**第二个，只选了 20 个岗位，够不够？会不会有覆盖不到的场景？**

20 个是冷启动阶段的"黄金集"，不是评测集的全部。这 20 个岗位我们在选取时做了两个维度的交叉覆盖：**职能维度**（技术、产品、销售、运营、职能）× **层级维度**（中级、高级、专家/管理层），确保覆盖猎聘主站上搜索量最大、同时搜索准确率最难保障的场景。每个岗位对应多轮评测，实际产生的评测数据点是**20 岗位 × 40 候选人 = 800 个匹配度判断**，不是 20 条数据。而且上线后，真实 HR 的每一次搜索都会自动进入评测样本池，持续扩充覆盖范围。

---

### 第二块：Agent 全链路稳定性——流程是否正确、稳定、可控

这一块测的不是"搜出来的人对不对"，而是**Agent 在整套流程中每一步是否正确触发了对应的 Skill、工具和接口**。

具体覆盖的链路是：**需求澄清 → 候选人搜索 → 结果筛选 → 二次确认 → 候选人触达**，每个环节我们都设计了三类测试场景：

**第一类，正常输入。** HR 的需求清晰、信息完整，验证 Agent 能否在标准场景下稳定跑通全流程，不出现多余的步骤、不遗漏关键环节。

**第二类，边界输入。** 包括几种典型情况：
- 需求模糊："帮我找个差不多的人"——Agent 是否会主动追问，而不是瞎搜
- 需求矛盾："要应届生但要有 3 年经验"——Agent 是否能识别冲突并提示
- 需求中途变更："算了不要北京的了，看上海的"——Agent 是否记住历史约束并正确调整
- 信息缺失：只说了职能没说城市、薪资——Agent 是否逐项补齐

**第三类，异常场景。** 包括：
- 候选人库中没有匹配结果时，Agent 是硬凑结果还是合理告知"没有合适的"
- 工具调用失败时，Agent 能否自动重试或降级处理
- HR 试图获取候选人隐私信息（手机号、身份证号）时，Agent 是否拒绝

**评测标准分成三类指标：**

| 指标类型 | 测什么 | 怎么评 |
|---|---|---|
| 结果指标 | 最终推荐的候选人是否匹配 HR 需求 | LLM Judge + 人工复核 |
| 过程指标 | 每一步 Skill 触发是否正确、是否有多余或遗漏的步骤 | 规则自动判断 |
| 安全指标 | 是否泄露隐私、是否越权操作 | 规则硬门槛，一票否决 |

---

### 汇总

**所以我们的评测逻辑是：第一块保证"搜得准"，第二块保证"流程稳"。** 搜得准但流程不稳，用户体验割裂；流程稳但搜不准，功能没有价值。两块缺一不可，分别对应 Agent 的"智商"和"稳定性"。冷启动阶段先用这 20 个黄金岗位建立基准线，上线后通过真实用户数据持续扩充评测样本，形成**离线评测 → 线上采样 → Bad Case 回流 → 回归验证**的闭环。

---

整段口述大概 2.5-3 分钟。面试官听到的逻辑线是：**为什么要分两块 → 每块怎么测 → 预期的质疑怎么回应 → 两块之间的关系是什么**。每个问题都有自洽的答案，不会留下"这个你怎么考虑的"的悬空感。




## cli 和mcp 的区别


## 一、核心结论（一句话定义）

> CLI 和 MCP 本质上是两种不同的 **Agent 工具调用范式**——一个是**直接执行**，一个是**协议中转**。

---

## 二、快速定义

| | CLI | MCP |
|---|---|---|
| **本质** | 通过命令行**直接调用**系统能力 | 为 AI 提供一套**工具说明书 + 调用规范**的协议 |

---

## 三、三维度对比结构

### 1. 工具认知方式

- **MCP**：模型需要**先读说明书**，理解工具能力，再决定如何调用
- **CLI**：模型**直接通过命令调用**，不需要复杂的描述和理解过程

### 2. 调用路径

```
MCP 路径：模型 → MCP Server → API（多一层中转）
CLI 路径：模型 → 命令行 → API（少一层中转，更直接）
```

### 3. 成本与效率

| | MCP | CLI |
|---|---|---|
| 上下文长度 | 长（需要加载工具描述） | 短 |
| Token 消耗 | 大 | 小 |
| 调用成本 | 高 | 低 |
| 整体效率 | 较重 | 轻量 |

---

## 四、具体例子：将会议记录写入 Notion

**MCP 方式：**
1. 读取工具说明书 → 了解 Notion 工具的能力
2. 选择合适工具 → 确定用哪个 MCP Server
3. 填写参数 → 按照说明书格式构造请求
4. 发起调用 → 通过 MCP Server 转发到 Notion API

**CLI 方式：**
1. 直接执行命令 → 调用 Notion API
2. 完成写入 → 无需中间层解释

---

## 五、深度理解（面试加分句）

> **MCP 解决的是让模型「知道怎么用」工具；CLI 解决的是让模型「直接用」工具。**

---

## 六、面试官追问：趋势怎么看？

### 演进逻辑

```
早期：模型能力弱 → 需要 MCP 这种「说明书体系」辅助理解
现在：模型变强了 → 理解力、推理力提升 → 不再需要重中间层
       → CLI 这种更精炼的方式开始占优势
```

### 但 MCP 并没有消失

在**企业场景**中，MCP 仍然适合做中间件层，因为它天然支持：
- **权限控制**
- **工具统一接入**
- **安全治理**

---

## 七、总结金句（收尾用）

> Agent 工具调用的未来**不是单选题**，而是：
>
> **轻量执行（CLI）+ 企业治理（MCP）的组合**

---

## 八、答题结构速记

```
1. 定性：一句话定义本质区别
2. 定义：分别快速解释 CLI 和 MCP
3. 对比：三个维度（认知方式/调用路径/成本效率）
4. 举例：一个具体场景对比两种方式
5. 深化：一句核心洞察（知道怎么用 vs 直接用）
6. 趋势：模型变强 → CLI 崛起，但 MCP 在企业中不可替代
7. 收尾：未来是组合方案，不是二选一
```



好的，给你按几个方向铺开，每个方向 3-5 个问题，你根据现场氛围和高管的背景挑着用。

---

## 方向一：AI 对 B 端产品的趋势判断

> **1. "AI Agent 这两年在 C 端的热度很高，但 B 端落地一直比较慢。您觉得企业级 AI 产品真正爆发的卡点是什么——是技术成熟度，还是企业侧的接受度？"**

- 直接跟你的 Agent 项目经历呼应，高管会觉得你踩过这个坑才问得出

> **2. "现在行业里有一种观点说，未来 B 端产品可能不再需要复杂的 UI 了，Agent 对话就能替代大部分操作界面。您怎么看这个判断？"**

- 这个问题有争议性，高管喜欢聊有争议的趋势话题
- 你做过 Agent 也做过传统产品，有立场但不先表态，听高管怎么说

> **3. "企业内部工具和外部 SaaS，在 AI 落地节奏上您觉得会一样吗？内部系统的优势和挑战分别是什么？"**

- 直接切到字节内部系统的定位，高管会觉得你真的在思考这个部门的战略处境

> **4. "很多公司现在都在做内部 AI 工具，但真正用起来的不多。您觉得一个内部 AI 产品从'做出来'到'用起来'，最关键的那一步是什么？"**

- 你做过 Agent 的真实 HR 试用和灰度验证，这个问题跟你经历完全契合
- 高管回答时你可以在心里对照自己的经验，面试结束后也能复盘

---

## 方向二：产品人的成长与能力模型

> **5. "在您的观察里，一个产品人从初级到高级，最核心的能力跃迁发生在哪个阶段？是方法论的成熟，还是对业务本质理解的加深？"**

- 经典但好用，高管通常愿意分享自己的成长路径
- 你能从中听出这个团队看重什么特质

> **6. "您觉得做 AI 产品和做传统互联网产品，对产品经理的要求最大的不同在哪里？"**

- 直接跟你转型 AI 产品的经历对应
- 高管如果也是从传统产品转过来的，会有很多共鸣可以讲

> **7. "To B 产品经理经常被说'离用户远'、'需求不性感'。您觉得做 To B 产品的人，怎么保持对用户真实需求的敏感度？"**

- 你做过 HR 访谈、灰度用户验证，这个问题背后是你已经在做的事
- 高管会觉得你不是在空想，而是在找系统性方法

> **8. "您带过的优秀产品人，有没有一些共性？不是说具体技能，而是思维方式或者做事习惯上的。"**

- 这个问题很讨巧——高管喜欢回忆自己培养过的人
- 你听到的共性可以直接变成你实习期间的行为准则

---

## 方向三：团队与组织视角

> **9. "这个部门同时覆盖人事、财务、法务多个领域，AI 产品团队的组织方式是按业务域分，还是按 AI 能力分？哪种您觉得更有效？"**

- 跟 JD 里写的"覆盖多个领域"直接相关
- 这个问题不问细节，问的是组织逻辑，高管愿意聊

> **10. "字节内部信息系统服务的用户规模很大，AI 产品的迭代节奏跟外部 C 端产品会有什么不同吗？"**

- 你做过 A/B 实验和灰度，但都是对外产品，这里在问内部产品的节奏差异
- 间接表达你对这个岗位有具体想象

---

## 方向四：行业格局与竞争

> **11. "现在企业级 AI 产品赛道里，您觉得大厂自研内部工具和创业公司做 SaaS，长期来看谁更有优势？"**

- 有深度，且跟字节自研内部系统的定位直接相关
- 高管通常对行业格局有判断，聊起来不会冷场

> **12. "有人说 AI 会重新洗牌 B 端产品格局，也有人说大公司的护城河很难被颠覆。您站在字节内部系统的视角，更倾向于哪种判断？"**

- 这个问题让高管站在自己部门的角度说话，他通常会认真回答
- 你不需要表态，只需要接住他的观点做自然追问

# soul 原则
版本一:回答"你怎么分析一个产品?"
我通常会分四层分析一个产品。第一是战略层，关注它选择做什么，以及主动放弃了什么;第二是体验层，关注它营造了怎样的产品氛围;第三是关系层，关注它重新连接了哪些用户、内容和创作者;第四是生态层，关注用户、创作者、平台和商业伙伴能否形成长期循环。
例如小红书，它的核心不只是发布笔记，而是通过真实经验影响用户的生活方式和消费决策。它在内容上强调生活感和个人经验，在关系上连接用户、创作者和品牌，在商业上则依赖社区信任。因此我会认为，小红书最重要的壁垒不是内容形式，而是用户对内容真实性和决策价值的信任。
版本二:回答“分析一下小红书”
我认为小红书的核心定位是生活方式社区，同时也是消费决策平台。从战略上看，它没有完全走纯娱乐内容平台的路线，而是强调用户主动搜索、经验分享和生活方式表达。从产品氛围看，它强调真实感、审美和个人经验。用户发布内容不仅是在介绍商品，也是在表达自己的生活方式和身份。
从用户连接看，小红书把内容和消费决策连接起来，形成了"内容一经验一信任一消费"的链路。用户可能因为一篇笔记决定去哪里旅行、买什么产品，或者采用什么生活方式。从生态看，它连接了普通用户、创作者、品牌和商家。平台的关键是维护内容可信度，因为一旦用户认为所有内容都只是广告，社区信任就会被破坏。
所以我认为小红书的核心壁垒是内容信任和决策影响力，而不是笔记这种内容形式本身。
版本三:回答“微信和抖音有什么区别?"
微信的核心是关系和服务，抖音的核心是内容分发和注意力效率。微信主要依靠熟人关系链，用户通常带着明确任务进入，比如聊天、支付、处理工作和使用服务。抖音则更多依赖算法推荐，用户可能不知道自己想看什么，但平台能行为反馈持续给出内容。微信的壁垒是强关系链和基础设施属性，抖音的壁垒是推荐效率、内容供给和商业化能力。AL




# 美图AB实验

# 该项目AB实验设计详解

---

## 对应7步流程，逐步拆解

### 第1步：明确实验策略和目的

**策略：** 上线AI证件照全自动化生成+付费高清下载功能

**目的：** 验证该功能能否有效**提升APP大盘整体付费率**，从而推动商业化收入增长

**话术示例：**
> 我们当时判断海外证件照市场存在供给空白，想验证的是：如果上线AI全自动化证件照生成，并配合「免费预览→付费高清下载」的转化漏斗，是否能有效提升我们APP大盘的整体付费率。

---

### 第2步：选指标

| 指标类型 | 具体指标 | 说明 |
|----------|----------|------|
| **核心指标**（1个） | APP大盘整体付费率 | 直接衡量策略是否带来付费转化 |
| **护栏指标** | GMV（总交易额）、用户DAU | 确保功能上线不会损害大盘收入和用户活跃 |
| **相关指标** | 证件照功能渗透率、高清下载转化率、用户使用时长、次日/7日留存率 | 观察但不决定实验成败 |

**北极星指标 vs 核心指标的区分（面试加分项）：**

> 我们部门这个阶段的**北极星指标**是整体商业化收入（GMV）。为了达成这个目标，我们拆解了多个策略方向，其中我负责的这个证件照项目，其**核心指标**是APP大盘整体付费率。另外还有其他同事负责的比如会员转化优化、广告变现等策略，各自有不同的核心指标，但最终都是服务于GMV这个北极星。

---

### 第3步：计算最小样本量

**公式：** N = f(α, β, σ, δ)

| 参数 | 值 | 说明 |
|------|-----|------|
| α（一类错误） | 0.05 | 允许5%的弃真概率 |
| β（二类错误） | 0.2 | 允许20%的取伪概率 |
| σ（方差） | 基于历史付费率数据计算 | 付费率本身波动不大，方差相对可控 |
| δ（预期最小提升） | 预设约1~2PP | 至少提升多少我们认为策略有业务价值 |

> **话术：** 我们基于历史数据中大盘付费率的波动情况，估算出方差σ，再结合我们预设的最小可接受提升值δ（约1~2个百分点），代入公式算出最小所需样本量大约在数百万量级。因为我们平台日活较高，最终确定900万样本，2周周期可以覆盖。

---

### 第4步：样本分流

> 基于用户ID进行哈希函数编码，随机按1:1比例分配到实验组和对照组。实验组可以看到并使用AI证件照功能，对照组不展示该功能入口。

**关键点：**
- 用户ID哈希 → 保证随机性
- 1:1分流 → 实验组450万，对照组450万
- 分流后用户在各自组内不切换（粘性分流）

---

### 第5步：确定实验周期

| 考虑因素 | 本项目做法 |
|----------|-----------|
| **最小样本量** | 900万样本，日活足够，2周可覆盖 |
| **周期性** | 跑满2周（14天），覆盖至少2个完整的工作日/周末周期 |
| **新奇效应** | AI证件照属于新功能，用户初次使用可能有尝鲜心理。2周周期基本可以让新奇效应衰减，最终数据取稳定后的表现 |

> **话术：** 我们最终跑了2周。一方面确保样本量充足；另一方面覆盖完整的周期性，消除工作日和周末的行为差异；同时证件照作为新功能，初期可能有新奇效应，2周时间让数据趋于稳定后再评估最终效果。

---

### 第6步：AA实验

> 在正式推策略之前，我们先跑了一轮AA实验。把实验组和对照组分好后，**不推证件照功能**，观察两组的核心指标（付费率）是否有显著差异。确认无差异后，才正式进入AB阶段。

**如果AA有差异：** 重新分流，重跑AA，直到两组无显著差异。

---

### 第7步：AB实验 + 显著性检验

**实验结果：**

| 指标 | 结果 |
|------|------|
| 样本量 | 900万 |
| 周期 | 2周 |
| 核心指标提升 | 付费率**净提升+2.1PP** |
| P值 | **p < 0.05** |
| Z值 | Z > 1.96（满足统计学显著） |
| 业务显著 | +2.1PP ≥ δ（满足业务显著） |

**双重显著判断：**

> 最终实验结果是实验组相比对照组付费率净提升+2.1个百分点，p < 0.05，Z > 1.96，满足**统计学显著**。同时+2.1PP超过了我们预设的最小提升标准δ，满足**业务显著**。两项均满足，说明这个策略有效，可以全量上线。

## 可能的追问及回答

### 追问1：护栏指标有异常吗？

> 没有。GMV和DAU在实验期间没有出现下降，说明该功能对大盘没有负面影响，反而通过付费率提升带动了GMV增长。

### 追问2：有没有遇到新奇效应？

> 有的。上线前3天实验组的付费率提升幅度比最终结果更高，大约在+3%左右，后续逐渐回落并稳定在+2.1PP。说明初期确实存在一定的新奇效应，但我们跑满了2周，取的是稳定后的数据。

### 追问3：样本量怎么算出来的？

> 基于Z值公式，Z = (实验组均值 - 对照组均值) / √(方差/样本量)，我们反推所需的最小样本量。α取0.05对应Z临界值1.96，β取0.2，结合历史付费率的方差σ和预设的最小提升δ，算出所需样本量。我们平台海外DAU足够高，900万样本在2周内可以轻松覆盖。

### 追问4：统计学显著但业务不显著怎么办？

> 如果出现这种情况，说明虽然实验组和对照组有统计学上的差异，但提升幅度太小，达不到业务预期。这时候需要回到策略本身去优化，比如优化付费转化漏斗、调整定价策略等，重新设计实验。
