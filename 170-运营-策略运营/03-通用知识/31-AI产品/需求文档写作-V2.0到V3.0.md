# 需求文档 V2.0 → V3.0：掌握这种思维，让研发追着你写需求

**视频来源**：秀明 · 需求文档完整指南 第五期（V2.0 → V3.0）
**发布日期**：2025-01-27
**延续案例**：手机号验证码注册（同一需求从 V0.1 写到 V3.0）

---

## 一、V3.0 的定位

- **定义**：高阶版 / 理想状态
- **核心目标**：需求文档能**一次性通过**，产品经理成为受研发信任的靠谱搭档
- **终极境界**：研发看完文档后觉得**不需要评审**，直接开发即可

---

## 二、5 大能力升级总览

| # | 升级维度 | 核心要点 |
|---|---------|---------|
| 1 | **需求背景阐述** | 更有深度，用数据说话，说服自己也说服同事 |
| 2 | **模块与领域意识** | 有整体设计思维，将功能抽象为可复用的服务/模块 |
| 3 | **表达精准度** | 消除自然语言的二义性，举例子、给图、给参照 |
| 4 | **框架性与拓展性** | 搭架子——方便自己和后续产品经理往里填东西 |
| 5 | **用户体验意识** | 更站在用户角度，注重交互和体验细节 |

## 三、升级 ①：需求背景的深度阐述

### 3.1 两个目的

| 目的 | 具体说明 |
|------|---------|
| **说服自己** | 在整理需求时就要想清楚"我为什么要做这个需求"，想清楚了才能做好 |
| **说服同事** | 让研发、测试、老板知道这个需求的价值，从而重视它、配合推进 |

### 3.2 V3.0 背景写法（以注册需求为例）

**背景升级——从空泛到有数据冲击感**：

| 维度 | V1.0 / V2.0 写法 | V3.0 写法 |
|------|-----------------|----------|
| 人力成本 | 没有注册流程，靠后台开 | 需要专人每天帮开通新账号，流程繁琐枯燥，可释放该人力去做更有价值的事 |
| 用户流失 | 未提及 | 由于注册时间长，部分用户等不及就用了竞品；可对比竞品注册流程（冲击感更强，汇报时效果好） |
| 战略对齐 | 未提及 | 明年公司目标是新用户翻倍，按预期推广节奏，注册将成为拓客**卡点**，必须优化 |
| 未来价值 | 未提及 | 后续裂变营销（老带新）依赖底层注册能力，需提前布局 |

> **金句**："需求背景里有些事不能讲出来，但绝大部分都应该想清楚。"
> 
> **价值与优先级的关系**：背景越充分，需求优先级越高——"公司明年要新用户翻倍"这句话一出来，这个需求的优先级立刻上去了。

## 四、升级 ②：模块与领域意识——整体设计

这是 V3.0 **最核心的思维升级**。

### 4.1 将注册功能抽象为"注册模块/服务"

**V2.0 的思维**：我做了一个注册功能。
**V3.0 的思维**：我做了一个**注册服务**，它是一个基础能力，所有需要注册的地方都可以调用它。

**哪些场景会复用注册服务？**

| 场景 | 说明 |
|------|------|
| **登录页** | 登录与注册天然关联 |
| **内容页**（如 B 站看视频） | 微信跳转 App → 想评论 → 引导注册 → 注册后评论 |
| **拉新活动页** | 活动拉新后需要注册，页面不同但底层注册服务相同（可能是弹窗，可能是完整页面） |
| **裂变营销** | 老带新场景依赖注册能力 |
| **第三方跳转注册** | 从外部渠道进来的用户也需要注册 |

> **关键认知**：页面不一样，但**底层服务是同一个**。你从一开始规划的时候就要想好——它能为所有人服务。

### 4.2 支持"调用方自定义跳转"

**V0.1 → V2.0**：注册成功后统一跳转首页。
**V3.0**：注册服务提供**参数化跳转**能力——调用方可以通过 URL 参数（如视频唯一 ID）指定注册成功后的跳转目的地。

**示例**：
- 用户 A 分享了视频给用户 B
- B 从未注册过
- B 点击链接 → 跳转注册页（URL 中携带视频 ID 参数）
- B 注册成功 → 自动跳转回该视频页，而非首页

> "这就是基础能力。从一开始就把东西设计好了——我只会在这个基础上累加，不会推翻重来。这就是信任的累积。"

### 4.3 短信服务商路由机制（抽象服务）

**核心概念**：将短信发送能力抽象为一个独立服务，并设计**路由机制**来适配不同地区/不同服务商。

**本次实现**（MVP）：
- 仅对接了服务商 XX，服务于**中国大陆地区**
- 特点：短信送达率高、费用低

**未来规划**（本次不做，但提前布局）：

| 扩展方向 | 说明 |
|---------|------|
| **跨境/海外** | 如果业务国际化，大陆服务商不支持海外或太贵，需接入其他服务商 |
| **路由机制** | 配置不同国家/地区 → 使用不同短信服务商 |
| **多场景复用** | 手机登录验证码、修改密码验证码、修改信息验证码……都走这个服务 |

**哪些地方会用到短信服务？**
- 手机验证码登录
- 修改密码
- 修改绑定手机号
- 其他需要短信验证的场景

> **展示给研发的目的**：即使本次不做，也要让他们知道你的规划——"这个产品经理是有大局观的。"

## 五、升级 ③：表达精准度——消除二义性

### 5.1 引用与抽象

V3.0 将**相同含义的描述**抽成独立用例，其他地方通过**引用**调用：

| 引用目标 | 内容 | 引用位置 |
|---------|------|---------|
| **用例 1.3 - 手机号字段** | 手机号的格式校验、位数校验、前缀校验等 | 每次需要校验手机号的地方 |
| **用例 1.3 - 验证码字段** | 验证码的校验逻辑、与手机号的匹配关系 | 每次需要校验验证码的地方 |
| **用例 1.5 - 短信内容** | 短信模板文案 | 组装短信时引用 |

> **引用的价值**：
> - 后期修改只改用例本身，所有引用处自动更新
> - 新来的产品经理看用例就知道完整逻辑，不用去找研发逐个对代码

### 5.2 举例子消除歧义

V3.0 在描述时大量使用**举例**来消除二义性：

> "什么叫视频页？什么叫拉新活动？有些人可能不懂——所以我把这些东西描述清楚。"

**举例的方式**：
- **场景举例**：A 分享视频给 B，B 未注册过，跳转注册页……
- **对比举例**：竞品的注册流程是怎样的，我们差在哪
- **反例举例**：如果输入了座机号，会怎样

> **方法论**：让一件事说清楚有三个手段——① 样式描述清楚（图+文）② 举例子 ③ 正反面对比

## 六、升级 ④：框架性与拓展性——搭架子

### 6.1 文档结构的"可累加性"

V3.0 的文档结构是**架子**——后续迭代只需要往里填东西，不用推翻重来：

| 版本 | 更新内容 | 操作方式 |
|------|---------|---------|
| **V3.0** | 基础注册流程 + 整体设计 | 搭好完整框架 |
| **V3.1** | 手机号前缀校验（138/139/182…） | 在"用例 1.3 手机号字段"中新增前缀枚举；文档中加"V3.1"标注，研发搜索即可定位 |
| **V3.2** | 支持多区号（多地区手机号注册） | 新增区号下拉框的数据源、枚举项；增加根据 IP 自动选择区号的逻辑 |

### 6.2 迭代标注方式

在文档中用**版本号标注**新增/修改的内容：

```
【V3.1】手机号前三位校验：138、182、139……（枚举）
         举例：输入 158XXXXXXXX → 校验不通过，因为前缀不在枚举中
```

> 研发搜索"V3.1"就能精准定位本次改了什么——**高效、零歧义**。

### 6.3 V3.2 示例：多区号注册

新增内容：
- 区号下拉框（Dropdown）
- 数据源：XX 网站（提供全球区号数据）
- 智能选择：根据用户 IP 自动选择对应地区的区号
- 对应关系表：IP 地区 → 区号映射

> **搭架子的意义**：V3.0 时区号只有中国大陆（+86），但结构上已经预留了下拉框。V3.2 只需要往里加枚举项，不改结构。

## 七、升级 ⑤：用户体验与交互细节

### 7.1 Toast 体验的完整描述

V3.0 不只说"弹个提示"，而是**精确描述每一种 Toast**：

| 场景 | Toast 样式 | 文案示例 |
|------|-----------|---------|
| 验证码发送成功 | 成功样式 Toast | "验证码已发送" |
| 验证码发送失败 | 失败样式 Toast | "发送失败，请稍后重试" |
| 注册成功 | 成功样式 Toast | "注册成功" |
| 手机号已注册 | 错误样式 Toast | "该手机号已注册" |
| 验证码错误 | 错误样式 Toast | "验证码错误" |

### 7.2 防重复点击的完整逻辑

**V0.1 的问题**：如果用户连续点击 N 次发送验证码，发 N 次还是 1 次？

**V3.0 的回答**：

```
- 点击发送后，按钮置灰，显示 60 秒倒计时
- 60 秒内交互上不可再次点击
- 即使用户通过技术手段绕过前端限制多次触发：
  → 10 分钟内相同手机号视为同一次请求，使用同一个验证码
  → 不会产生新验证码，不会多发短信
```

> 这就把 V0.1 时研发问的所有问题都**一次性堵住了**。

## 八、技术细节的边界——不建议写代码

### 8.1 不建议做的事情

| 不建议 | 原因 |
|--------|------|
| **直接贴代码到文档中** | 受众未必都懂代码（测试、UI、其他产品经理） |
| 过于技术化的实现描述 | 文档的延续性差——别人不会改你的代码，无法迭代 |

### 8.2 可以做的适度技术表达

| 可以做 | 原因 |
|--------|------|
| **JSON 格式** | 大多数 B 端产品经理能看懂，简单的 key-value 结构 |
| 接口入参/出参的字段描述 | 用自然语言 + 字段名表即可 |
| 表名 + 字段名 | 唯一、无歧义，研发可直接对照开发 |
| 请求头信息（URL、账号、Token） | 附录中列出，研发直接参考 |

> **原则**：文档是**所有人的产出前提**。测试可能只做黑盒测试，UI 不懂代码，其他产品经理也需要能读懂和迭代你的文档。

## 九、V3.0 完整文档结构总览

| 章节 | 内容 |
|------|------|
| **1. 需求背景** | 业务背景（数据支撑）、痛点分析、竞品对比、战略对齐、未来价值 |
| **2. 名词解释** | 所有可能有歧义的术语定义 |
| **3. 整体设计** | 模块抽象（注册服务）、领域划分（短信路由机制）、拓展规划 |
| **4. 流程图** | 正向流程 + 异常流程 |
| **5. 交互字段表** | 每个字段的必填、样式、Placeholder、校验规则、报错文案 |
| **6. 时序图** | 跨系统接口调用、数据流转 |
| **7. 接口描述** | 入参/出参、字段含义、请求头信息、第三方接口地址 |
| **8. 用例引用** | 手机号字段(1.3)、验证码字段(1.3)、短信内容(1.5) 等独立用例 |
| **9. 附录** | 短信服务商接口详情、区号数据源、Token 信息等 |

> **最终字数**：约 2500~3000 字，没有废话，每一段都有存在的理由。

## 十、V0.1 → V3.0 全系列对比总结

| 维度 | V0.1（不可开发） | V1.0（入门） | V2.0（合格） | V3.0（高阶） |
|------|----------------|-------------|-------------|-------------|
| **背景** | 一句话 | 四要素 | 四要素 | 数据支撑 + 竞品对比 + 战略对齐 |
| **整体设计** | 无 | 无 | 无 | 模块抽象 + 领域意识 + 拓展规划 |
| **格式** | 无格式 | Markdown 基础 | 符号标记体系 | 全套标记 + 颜色编码 + 版本标注 |
| **流程** | 无 | 正向+异常流程图 | 流程图 + 时序图 | 流程图 + 时序图 + 引用抽象 |
| **交互** | 未涉及 | 文字粗述 | 结构化表格 | 完整字段表 + 体验细节 + Toast 描述 |
| **数据/接口** | 未涉及 | 未涉及 | 入参出参 | 表名+字段名 + 请求头 + 路由机制规划 |
| **引用与抽象** | 无 | 无 | 文案引用 | 字段/逻辑/接口全面引用抽象 |
| **可迭代性** | 无法迭代 | 勉强迭代 | 可迭代 | 架子可累加，版本标注精准定位 |
| **研发反应** | "这啥？评审过不了" | "勉强能看" | "挺靠谱" | "不用评审了，直接开发" |
