# Agent 评测集设计

## 一句话理解

Agent 评测不是验证“输入 A 是否输出固定答案 B”，而是验证 Agent 能否在真实、不确定的环境中，用合理的过程把一件事完成，并且处于可控、安全、可解释的范围内。

> 真实任务 → 评测样本 → 自动运行 → 结果与轨迹 → Bad Case 归因 → 回归集 → 版本门禁 → 线上数据回流

## 一、当前资料集的定位

当前资料来自一批 Agent 评测相关的小红书内容，包含 20 条笔记、104 张配图，主题覆盖：

- GAIA、SimpleQA、Live Benchmark 等通用 Benchmark
- Agent 多轮对话数据集构造
- 黄金集、边界集、回归集、随机集
- LLM-as-Judge、人工复核和自动化评测管道
- RAG 检索质量、Skill 测试、浏览器 Agent
- 离线评测、线上监控、灰度发布和 Bad Case 数据飞轮

这批资料目前更像“方法论素材库”，还不是可以直接运行的评测集。下一步要把文章中的观点转成：用户任务、环境、可用工具、预期行为、通过标准和失败归因。

## 二、整体设计思路

一条合格的 Agent 评测样本，最小单位不是一句 Prompt，而是：

> 任务目标 + 初始环境 + 用户输入 + 可用工具 + 预期结果 + 通过标准 + 失败归因

多轮任务还需要加入：

> 多轮对话 + 中途变化/纠错 + 最终结局

因此要优先设计“任务题”，而不是简单的问答题。

例如：

- 问答题：请告诉我某个产品的价格。
- 任务题：请搜索三个平台的价格，排除过期信息，整理成表格，并给出推荐。

后者才能同时评估检索、判断、工具调用、信息整合和最终交付能力。

## 三、评测集的分层方式

### 1. 按 Agent 能力分层

至少覆盖以下能力：

| 能力 | 评测重点 |
| --- | --- |
| 意图理解 | 是否理解用户真正目标，而不是只抓关键词 |
| 需求澄清 | 信息不足时是否会追问 |
| 规划能力 | 是否拆解任务并选择合理步骤 |
| 工具调用 | 工具是否选对、参数是否正确 |
| 检索能力 | 是否找到相关、最新、可信的信息 |
| 多轮记忆 | 是否记住前文和用户约束 |
| 动态调整 | 用户改需求后是否能重新规划 |
| 结果交付 | 是否产出完整、准确、可执行的结果 |
| 异常恢复 | 工具失败、信息冲突时能否自救 |
| 安全合规 | 是否拒绝高风险或越权操作 |
| 成本效率 | 是否出现无效循环、过多步骤和不必要调用 |

### 2. 按场景风险分层

建议至少包含四类数据：

- 黄金集：核心业务任务，代表最重要、最常用的路径
- 正常集：信息完整、流程顺利的常规任务
- 边界集：模糊、冲突、缺失、异常或容易误解的输入
- 回归集：历史 Bad Case、线上事故和曾经修复过的问题

可进一步增加：

- 对抗集：提示词注入、诱导越权、恶意工具调用
- 长链路集：需要多步检索、多个工具和复杂判断
- 新鲜度集：要求实时信息，防止模型依赖过时知识
- 污染防控集：测试模型是否只是背过答案

冷启动时可使用一个实用比例：黄金集 20%、正常集 30%、边界/对抗集 25%、回归集 25%。比例不是硬规则；核心业务和安全场景应优先保证覆盖。

### 3. 按测试生命周期分层

1. 开发阶段：工具、Prompt、RAG、路由的局部测试
2. 集成阶段：多个组件组合后的行为测试
3. 上线前：完整任务的离线评测
4. 灰度阶段：小流量线上观察
5. 线上阶段：持续采样、审计和 Bad Case 回流
6. 版本回归：模型、Prompt、工具或知识库变更后重新运行

## 四、评测样本字段设计

| 字段 | 说明 |
| --- | --- |
| case_id | 唯一编号 |
| domain | 业务领域 |
| task_type | 检索、规划、执行、问答、分析等 |
| difficulty | 简单、中等、困难 |
| risk_level | 低、中、高 |
| user_goal | 用户真实目标 |
| user_prompt | 初始输入 |
| context | 历史对话、可见上下文和环境状态 |
| available_tools | 允许使用的工具 |
| hidden_constraints | 不直接告诉 Agent 的限制 |
| expected_behavior | 期望行为 |
| success_criteria | 通过标准 |
| failure_criteria | 明确失败条件 |
| reference_answer | 参考答案或答案要点 |
| max_steps | 最大允许步骤数 |
| max_cost | 最大 Token、费用或时间 |
| expected_tool_trace | 期望工具调用轨迹 |
| judge_type | 规则、程序、LLM Judge 或人工 |
| source | 来源或原始 Bad Case |
| version | 样本版本 |
| tags | 多轮、注入、过期信息、工具失败等标签 |

`reference_answer` 不一定是一段固定文本。对于 Agent，更适合记录：必须包含的事实、不得出现的错误、必须完成的动作和可接受的答案范围。

## 五、评测标准

### 1. 硬指标

适合程序自动判断：

- 是否完成任务
- 是否调用正确工具，参数是否正确
- 是否返回合法结构和必要字段
- 是否违反安全规则
- 是否超出最大步数、延迟、Token 或费用
- 是否引用了有效来源

### 2. 软指标

适合 LLM Judge 或人工复核：

- 事实准确性
- 相关性
- 完整性
- 可执行性
- 表达清晰度
- 是否符合用户约束
- 是否存在无依据推断
- 是否合理表达不确定性

建议采用 0–4 分制：

- 4 分：完全正确，目标达成，无明显问题
- 3 分：基本完成，有轻微瑕疵但不影响使用
- 2 分：部分完成，需要用户补救
- 1 分：方向基本错误或关键环节失败
- 0 分：未完成、虚构、越权或造成严重风险

### 3. 过程指标

- 是否在信息不足时先澄清
- 是否选择了合理工具
- 是否出现无意义循环或重复调用
- 是否使用了错误上下文
- 是否在失败后调整策略
- 是否提前停止或进行了不必要的高成本操作

最终答案正确，不代表过程可靠。需要同时检查结果、轨迹、安全和效率。

## 六、核心设计原则

### 原则一：任务导向，而不是答案导向

评测“事情有没有做成”，而不是“有没有复述标准答案”。

### 原则二：允许语义等价

不能因为措辞不同、步骤顺序略有差异就机械判错。只要目标一致、关键约束满足，就应该通过。

### 原则三：结果和过程分开评分

至少拆成结果质量、过程质量、安全性和效率，便于定位问题来自模型、Prompt、工具、知识库还是规则。

### 原则四：核心和高风险场景设置硬门槛

安全、支付、删除、医疗、法律、权限等任务不能只看平均分。严重安全违规应直接不通过。

### 原则五：优先收集 Bad Case

真实失败样本通常比简单成功样本更有价值。每次线上失败都应完成：复现 → 标注 → 归因 → 加入回归集 → 修复 → 重新验证。

### 原则六：评测环境必须可控

记录模型版本、Prompt 版本、工具版本、知识库版本、数据时间、网络环境和运行次数，否则分数无法可靠比较。

### 原则七：不要迷信单一总分

总分只能看趋势，不能替代分项指标。应单独关注核心任务成功率、高风险违规率、边界通过率、工具调用错误率、平均步骤数、P95/P99 延迟、Token/成本和回归集退化。

## 七、如何验收一套评测集

用以下问题检查：

1. 每条样本是否有明确的用户目标？
2. 是否说明了什么结果算成功？
3. 是否覆盖正常、异常、需求变更和失败恢复？
4. 是否包含真实业务约束，而不只是理想化 Prompt？
5. 是否能区分结果错误和过程错误？
6. 是否能自动评测大部分指标？
7. 是否有人工复核和 LLM Judge 校准机制？
8. 能否回答“Agent 在哪一步、因为什么失败”？

如果只能回答“这道题得了几分”，却不能定位失败原因，评测集还不够成熟。

## 八、从当前资料落地的下一步

把现有 20 条资料转成三类资产：

### 1. 方法论标签库

给每条资料打上数据集设计、指标、评测方法、线上监控、工具、风险等标签。

### 2. 可执行任务集

从文章中的观点抽取真实任务，补齐 Prompt、上下文、工具和成功标准。

### 3. 评测规则库

把“任务完成”“安全通过”“工具参数正确”“不超过 N 步”等内容转成可检查规则。

最终目标不是建立一个内容丰富的资料表，而是建立一套可持续运行的评测闭环。

## 九、面试表达版

如果面试官问“你会怎么设计 Agent 评测集”，可以这样回答：

> 我会先从真实业务任务出发，而不是从固定答案出发。每条样本包含用户目标、上下文、可用工具、预期行为、成功标准和失败标准。数据集会按能力覆盖意图理解、规划、工具调用、多轮记忆、异常恢复和安全，也会按风险拆成黄金集、正常集、边界集和回归集。评测时同时看最终结果和完整轨迹，分别衡量任务成功率、事实准确性、安全违规率、工具调用错误率、步骤数、延迟和成本。上线后把 Bad Case 持续回流成回归集，并在模型、Prompt、工具或知识库变化时自动跑评测，形成数据飞轮和发布门禁。核心原则是允许语义等价，但对安全和高风险问题设置硬门槛。
