## 一、这是什么？

这是一套给 **AI coding agent**（如 Claude Code、Codex 等）使用的工程化工作流技能包。它不是 prompt 合集，也不是 vibe coding，而是一套**结构化的工程实践指令**，让 AI agent 按照真实的软件工程方法论来工作。

核心价值：把演讲中提到的那些理念（Grill Me、共享语言、TDD、深模块架构）变成可以一键调用的命令。

---

## 二、前提条件

在开始之前，你需要：

| 条件 | 说明 |
|------|------|
| **Node.js** | 需要 npx 命令（Node.js 18+ 即可） |
| **一个 AI coding agent** | Claude Code / Codex / Cursor 等支持 skills 的 agent |
| **一个代码项目** | 你正在进行的项目，或准备新建一个 |
| **Git 仓库** | 项目需要是 git 仓库 |

确认 npx 可用：
```bash
npx --version
```

## 三、安装（30 秒）

### 第一步：运行安装命令

在你的终端中执行：

```bash
npx skills@latest add vinvcn/mattpocock-skills-zh-CN
```

### 第二步：选择 skills

运行后会出现一个交互式选择界面，让你勾选想安装的 skills。

**初次使用建议全选**，但至少确保包含以下核心 skills：

```
✅ /setup-matt-pocock-skills   ← 必选！其他 skills 依赖它的配置
✅ /grill-with-docs            ← 需求澄清（最常用）
✅ /grill-me                   ← 轻量版需求澄清
✅ /tdd                        ← 测试驱动开发
✅ /to-prd                     ← 生成 PRD 文档
✅ /to-issues                  ← 拆分为 issue
✅ /diagnose                   ← Bug 诊断
✅ /improve-codebase-architecture ← 架构改善
✅ /triage                     ← Issue 分诊
✅ /zoom-out                   ← 代码全局视角
```

### 第三步：选择要安装到哪个 agent

选择你正在使用的 AI coding agent（Claude Code / Codex 等）。

## 四、初始化配置

安装完成后，**必须先运行 setup skill**。

### 在你的 AI agent 中运行：

```
/setup-matt-pocock-skills
```

它会问你三个问题：

### 问题 1：使用哪个 issue tracker？

```
选项：
  → GitHub Issues
  → Linear
  → Local files（本地文件，不依赖外部服务）
```

- 如果你的项目在 GitHub 上 → 选 **GitHub Issues**
- 如果你没有 issue tracker → 选 **Local files**

### 问题 2：triage issues 用哪些 labels？

它会询问你在分诊 issues 时使用的标签体系，例如：
- `bug`、`feature`、`enhancement` 等
- 如果你不确定，让 setup 自动创建默认的即可

### 问题 3：docs 保存到哪里？

指定文档（PRD、ADR 等）的存放目录，默认是 `docs/`。

**配置完成后，你的项目目录结构大致如下：**

```
your-project/
├── docs/
│   └── adr/          ← 架构决策记录
├── CONTEXT.md        ← 共享语言/领域术语文件
├── AGENTS.md         ← Agent 行为配置
└── ...你的项目文件
```

## 五、核心 Skills 使用指南

### 1. `/grill-with-docs` — 需求澄清（最核心、最常用）

**何时使用：** 每次想做功能变更、新功能、重大修改之前

**使用方式：** 在 agent 中输入：

```
/grill-with-docs 我想给用户添加一个收藏功能，用户可以收藏文章并在个人主页查看
```

**会发生什么：**

1. Agent 会对照你项目的 `CONTEXT.md`（领域术语）来理解你的项目
2. Agent 会像"拷问者"一样连续追问你 20~60 个问题：
   - "收藏是按用户维度还是按设备维度？"
   - "收藏数量有上限吗？"
   - "收藏的文章被删除后怎么处理？"
   - "需要通知功能吗？"
   - ...一直问到所有设计分支都被厘清
3. 过程中 Agent 会自动更新 `CONTEXT.md` 和 ADR（架构决策记录）
4. 产出：清晰的需求文档 + 共享术语表 + 架构决策

**和 `/grill-me` 的区别：**

| | `/grill-me` | `/grill-with-docs` |
|---|---|---|
| 适用场景 | 任何计划/想法，不限于代码 | 代码项目中的变更 |
| 文档能力 | 无 | 自动更新 CONTEXT.md 和 ADR |
| 推荐度 | 一般 | **强烈推荐** |

---

### 2. `/tdd` — 测试驱动开发

**何时使用：** 开始实现一个功能或修 bug 时

**使用方式：**

```
/tdd 实现用户收藏文章的功能
```

**会发生什么：**

Agent 会严格遵循 **Red-Green-Refactor** 循环：

```
循环 {
  1. 🔴 Red：先写一个失败的测试
  2. 🟢 Green：写最少的代码让测试通过
  3. 🔵 Refactor：重构代码，改善设计
}
```

它会：
- 一次只做一个 vertical slice（垂直切片）
- 每次只写一个小测试
- 确保测试通过后才继续下一步
- 不会一次生成大量代码

**关键原则：** "反馈的速率就是你的速度上限"——这正是 TDD 强制 AI 遵守的。

---

### 3. `/diagnose` — Bug 诊断

**何时使用：** 遇到棘手的 bug、性能问题、难以复现的问题时

**使用方式：**

```
/diagnose 用户在移动端点击收藏按钮时偶尔会崩溃，错误日志是 ...
```

**会发生什么：**

Agent 按照纪律化的诊断循环工作：

```
Reproduce → Minimise → Hypothesise → Instrument → Fix → Regression Test
  复现      最小化      假设          插桩追踪     修复    回归测试
```

不会乱猜，不会瞎改代码，而是系统性地定位问题。

---

### 4. `/to-prd` — 生成产品需求文档

**何时使用：** 和 agent 讨论完需求后，想把讨论内容整理成正式文档

**使用方式：**

```
/to-prd
```

**注意：** 它不会重新访谈你，而是**综合当前对话中已经讨论过的内容**，整理成结构化的 PRD。

典型流程：先 `/grill-with-docs` → 讨论清楚后 → `/to-prd` 生成文档

---

### 5. `/to-issues` — 拆分为 Issues

**何时使用：** PRD 已经就绪，需要拆分为可独立领取的开发任务

**使用方式：**

```
/to-issues
```

**会发生什么：**

- 读取 PRD（或当前对话中的计划）
- 按 **vertical slices** 拆分成独立的 issue
- 每个 issue 可以独立开发、独立测试、独立交付
- 自动发布到你配置的 issue tracker（GitHub Issues / Linear / 本地文件）

---

### 6. `/improve-codebase-architecture` — 改善代码库架构

**何时使用：** 感觉代码库变成了 "ball of mud"（泥球），模块边界不清晰

**使用方式：**

```
/improve-codebase-architecture
```

**会发生什么：**

Agent 会：
1. 读取 `CONTEXT.md` 中的领域语言
2. 读取 `docs/adr/` 中的架构决策
3. 扫描代码库，找到可以"加深"的模块机会
4. 将相关的浅模块合并/重构为深模块（简单接口 + 复杂实现）

**建议：** 每隔几天跑一次，防止代码库退化。

---

### 7. `/zoom-out` — 全局视角

**何时使用：** 在某个具体代码区域感到困惑，需要理解更大上下文时

**使用方式：**

```
/zoom-out 这个 UserService 是怎么和订单模块交互的？
```

Agent 会跳出当前代码片段，给出系统级的上下文解释。

---

### 8. `/triage` — Issue 分诊

**何时使用：** 有一堆 issues 需要分类和排优先级时

**使用方式：**

```
/triage
```

按照状态机模型对 issues 进行分诊，分配 labels 和优先级。

## 七、CONTEXT.md 的重要性

`CONTEXT.md` 是整个体系的**核心文件**，相当于演讲中提到的"通用语言（Ubiquitous Language）"。

### 它的作用：
- 让 AI agent 理解你项目的领域术语
- 在所有技能之间共享项目上下文
- 随着 `/grill-with-docs` 等技能的使用自动更新

### 你应该怎么做：
- 定期阅读它，确保术语准确
- 和团队成员共享它
- 让它成为项目知识的"活文档"

## 八、实用技巧

### 技巧 1：不要跳过 Grill

> 每次想做变更，先 `/grill-with-docs`，哪怕你觉得需求已经很清楚了。

Grill 的价值不只是问问题，更是在过程中建立共享设计概念，防止 AI 跑偏。

### 技巧 2：接口自己设计，实现交给 AI

这是演讲中"深模块"策略的实践：
- 你自己设计模块的**接口**（函数签名、类型定义）
- AI 负责填充**实现**
- 用测试从外部验证

### 技巧 3：保持小步

> "反馈的速率就是你的速度上限。"

不要让 AI 一次生成太多代码。用 `/tdd` 确保每一步都有测试覆盖。

### 技巧 4：定期改善架构

每隔几天跑一次 `/improve-codebase-architecture`，就像打扫房间一样，防止代码库熵增。

### 技巧 5：混合使用

这些 skills 可以自由组合：
```
/grill-with-docs 需求讨论
    ↓
/to-prd 整理成文档
    ↓
/to-issues 拆分任务
    ↓
/tdd 逐个实现
    ↓
/diagnose 遇到 bug 时
    ↓
/zoom-out 迷茫时
    ↓
/improve-codebase-architecture 定期优化
```

## 九、FAQ

**Q: 需要付费吗？**
不需要，MIT 开源协议，免费使用。

**Q: 只能在 Claude Code 中用吗？**
不是，支持多种 AI coding agent（Claude Code、Codex 等），安装时选择对应 agent 即可。

**Q: 和原始英文版有什么区别？**
功能完全一致，文档和技能说明翻译为简体中文，目录名、skill name、命令、代码块保持英文不变，不破坏运行行为。

**Q: 安装后 skills 在哪里？**
在你项目的 `.claude-plugin` 或对应 agent 的配置目录中。

**Q: 可以自定义 skills 吗？**
可以。这些 skills 被设计为"小、易改、可组合"，你可以直接编辑 skill 文件来适配自己的工作流。
