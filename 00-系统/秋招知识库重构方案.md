# 秋招知识库重构方案

> 目标：把零散的项目资料、面经、录音、面试模板和复盘，组织成一个可以持续迭代的“面试准备操作系统”。

## 一、核心判断

当前仓库的问题不是内容太多，而是缺少“内容生命周期”：

```text
原始材料 → 事实提取 → 项目/业务知识 → 岗位面试模板 → 面试使用 → 面试复盘 → Bad Case 回流
```

建议借鉴 LLM Wiki V2，但不要把所有内容都直接编译成 Wiki。面试录音、面经和个人复盘都应保留原貌；只有经过确认、抽取和验证的内容，才进入可复用知识层。

## 二、推荐的顶层结构

```text
秋招/
├── 00-系统/                    # 系统说明、Schema、模板、索引、工作流
├── 01-Inbox/                   # 尚未处理的录音、面经、灵感、截图文字
├── 02-项目/                    # 项目事实库：经历、成果、决策、证据
├── 03-能力与知识/              # 可迁移的方法论与 AI/产品知识
├── 04-岗位准备/                # 按岗位/公司生成的面试准备包
├── 05-面试过程/                # 面试前、面试中、面试后的单场记录
├── 06-题库/                    # 通用题、业务题、追问题及标准答法
├── 07-训练与评测/              # Mock、表达训练、Agent 评测集
├── 08-素材/                    # 音频、字幕、PDF、图片等大文件
└── 99-归档/                    # 过期版本、已结束岗位、历史资料
```

## 三、各层的职责

### 00-系统：指令层

这里放“如何处理知识”的规则，不放具体业务知识：

- `README.md`：如何使用整个知识库
- `Schema/项目.md`：项目知识的字段规范
- `Schema/面试.md`：单场面试记录规范
- `Schema/面经.md`：外部面经的抽取规范
- `Schema/岗位准备.md`：岗位准备包规范
- `Templates/项目卡.md`
- `Templates/岗位准备包.md`
- `Templates/面试记录.md`
- `Templates/复盘.md`
- `Templates/面经处理.md`
- `索引/项目总览.md`
- `索引/岗位总览.md`

### 01-Inbox：原始输入层

只负责接收，不要求立即整理。每条材料先加最小元数据：来源、日期、关联公司/岗位、处理状态。

适合放：

- 面试录音转写
- 外部面经
- 用户原始反馈
- 临时想到的回答
- 截图 OCR、视频字幕、课程笔记

状态建议：`inbox → processing → compiled → archived`。

### 02-项目：个人事实层

这里是面试中最重要的“证据库”，记录你真正做过什么，不直接写成漂亮话。

每个项目建议拆成：

- 项目总览：背景、目标、角色、结果
- 事实时间线：发生了什么
- 决策记录：为什么这么做、有哪些备选方案
- 数据与证据：指标、实验、截图、链接
- 面试表达：30 秒、2 分钟、5 分钟版本
- 追问树：面试官可能继续问什么
- 风险与诚实边界：哪些是自己做的，哪些是团队成果，哪些只能说推测

当前内容的主要归属：

- `00-简历内容/剪映-音色克隆/` → `02-项目/剪映-音色克隆/`
- `00-简历内容/百度-玲珑中台/` → `02-项目/百度-玲珑中台/`
- `完整项目逻辑/` → 对应项目的事实与决策记录
- `需求文档/`、`AB实验/` → 作为项目证据或方法论引用，不再单独漂浮

### 03-能力与知识：编译后的通用层

只放跨项目可复用的知识，例如：

- AI 产品认知
- Agent 产品设计
- Agent 评测
- 数据分析与 AB 实验
- 产品 Sense
- 漏斗、费米估算、用户画像、技术选型
- 面试表达方法

当前内容的主要归属：

- `01-产品方法论/`
- `AI产品的认知要求/`
- `04-产品Sense/日常练习/`
- `02-AIGC策略/` 中可迁移的能力材料
- `评测准备/Agent评测集设计.md`

项目特定内容不应放这里；例如“玲珑项目的 30 条评测集”属于项目证据，“Agent 评测集如何设计”才属于通用知识。

### 04-岗位准备：面试前的交付层

这是每个目标岗位的“一次性作战包”，不能只是一堆链接。建议每个包固定包含：

```text
岗位准备包/
├── 00-岗位画像.md
├── 01-JD拆解.md
├── 02-公司与业务研究.md
├── 03-匹配项目.md
├── 04-业务面试模板.md
├── 05-高频题与回答.md
├── 06-可能追问.md
├── 07-反问问题.md
└── 08-面试前检查清单.md
```

这里的“业务面试模板”就是把 JD、公司研究、项目事实和历史面经编译后的产物。它不是原材料，也不是永久知识，而是面试前的版本化交付物。

当前内容的主要归属：

- `100-策略PM/` 至 `105-产品运营/` → `04-岗位准备/岗位画像/` 或能力索引
- `不同厂面试准备/` → `04-岗位准备/公司专项/`
- `产品转策略运营面试问答/` → 迁移为策略运营岗位准备与题库

### 05-面试过程：真实事件层

每一场面试单独建档，连接到岗位包、项目和题库：

```text
05-面试过程/
├── 2026-07-22-公司-岗位-一面.md
├── 2026-07-22-公司-岗位-一面-录音.md
└── 2026-07-22-公司-岗位-一面-复盘.md
```

录音转写属于原始事实；复盘属于个人判断。两者分开，避免把“我认为面试官在意评测”误写成面试官明确说过的话。

### 06-题库：可复用问答层

题库不按“某次面试出现过”组织，而按能力和面试阶段组织：

- 通用问题
- 业务一面
- 业务二面
- Leader 面
- 项目深挖
- AI 产品专项
- 数据与实验
- Agent 与评测
- 反问问题

每道题连接到：相关项目、适用岗位、参考答案、最近一次失分记录。

### 07-训练与评测：质量控制层

放 Mock 面试、表达训练、评测集和 Bad Case：

- Mock 原始记录
- Mock 复盘
- 表达问题清单
- Agent 评测集
- 面试回答评测标准
- Bad Case 回归集

这里可以复用你已有的 Agent 评测思路：不要只评“答案像不像”，还要评目标完成、事实准确、结构完整、追问承接、证据使用和风险边界。

## 四、单条材料的处理流水线

### 面经处理

```text
面经原文
→ 识别公司/岗位/轮次/时间
→ 提取面试官问题
→ 标注考察能力
→ 判断是否为高频问题
→ 关联项目与题库
→ 形成岗位准备包中的面试模板
```

### 面试录音处理

```text
录音/字幕
→ 保留原始转写
→ 区分面试官原话与自己的回答
→ 提取追问链
→ 标出事实、观点、猜测
→ 生成复盘
→ 形成新的题库题目和 Bad Case
```

### 项目材料处理

```text
原始项目资料
→ 建立事实卡
→ 提取角色、动作、决策、结果、证据
→ 补充数据口径与诚实边界
→ 编译成 30 秒/2 分钟/5 分钟表达
→ 关联到目标岗位准备包
```

## 五、YAML 元数据建议

原始材料：

```yaml
---
type: raw
source: interview_transcript | interview_experience | audio | note
company: 
role: 
interview_round: 
status: inbox | processing | compiled | archived
created: 2026-07-22
---
```

编译后的知识：

```yaml
---
type: knowledge
evidence_level: official | firsthand | transcript | community | inference
status: draft | candidate | verified | deprecated
source: 
related_projects: []
related_roles: []
reviewed: 2026-07-22
review_cycle: 30d
---
```

面试记录：

```yaml
---
type: interview
company: 
role: 
round: 
date: 2026-07-22
result: pending | pass | reject | unknown
prep_package: 
recording: 
review_status: pending | reviewed
---
```

## 六、最重要的边界

1. 原始资料永不覆盖，只能新增整理稿。
2. 事实、推断、建议必须区分。
3. 岗位准备包允许按 JD 定制，但不能反向污染项目事实。
4. 复盘结论必须注明证据来源和置信度。
5. 旧模板不删除，标记 `deprecated` 后归档。
6. 任何面试结果都要回流至少一条：新问题、回答缺口、表达问题或项目证据缺口。

## 七、建议的迁移顺序

### 第一阶段：先建系统，不移动内容

- 建立 `00-系统/`、`01-Inbox/`、`02-项目/`、`04-岗位准备/`、`05-面试过程/`、`06-题库/`、`07-训练与评测/`。
- 为现有核心项目和核心岗位建立索引。
- 先处理最近要投递的岗位，不追求一次性整理全库。

### 第二阶段：整理两条主线

- 主线 A：剪映音色克隆、AI 深度剪辑、一起教育、玲珑中台、周末活动 Agent。
- 主线 B：目标岗位的 JD → 公司业务 → 匹配项目 → 业务面试模板。

### 第三阶段：批量迁移和归档

- 将已确认内容迁移到新位置。
- 原位置保留重定向说明或别名，确认链接无误后再归档。
- 将面经和录音按公司、岗位、轮次补齐元数据。

## 八、一次面试的标准使用方式

```text
面试前：读取岗位准备包 + 相关项目表达 + 高频追问
面试中：只记录问题、追问、自己的原话和面试官反馈
面试后：生成复盘，标注事实/判断/猜测
复盘后：更新题库、项目表达、岗位模板和 Bad Case
定期：审查过期知识、冲突观点和长期未使用内容
```

## 九、当前仓库的关键重构结论

- `00-简历内容` 不是“简历文件夹”，应重构为项目事实库。
- `03-面试` 不是所有面试内容的总仓库，应拆为题库、岗位准备和面试过程。
- `面经` 是原始输入，不能直接当作答案库。
- `通用问题` 是题库，但需要增加项目链接、岗位链接和最近失分记录。
- `02-AIGC策略` 混合了知识、岗位准备、Mock 和冲刺计划，需要拆层。
- `评测准备` 应同时服务于 AI 产品知识学习和“玲珑项目”的面试证据，但两者要分开。

## 十、完成标准

当你可以从一个目标岗位出发，在 10 分钟内找到：

1. JD 要求和业务判断；
2. 最匹配的两个项目；
3. 每个项目的 30 秒、2 分钟、5 分钟版本；
4. 高频问题和可能追问；
5. 过去回答失败的地方；
6. 面试前最后检查清单；

这套知识库就从“资料收藏夹”变成了可运行的面试系统。
